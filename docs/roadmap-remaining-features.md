# 남은 기능 개발 로드맵 — 후원 결제 · AI 챗봇 · 이메일 인증

세 가지 미개발 기능의 개발 계획. 규모는 상대 표기(S/M/L)로만 제시(시간 추정은 근거 없이 하지 않음).

## 권장 진행 순서
1. **이메일 인증(S)** — 선행조건 없음(SMTP 완료), 비밀번호 재설정 인프라 재사용 → 가장 빠르게 완결
2. **AI 챗봇(M)** — 범위 정의 후 진행, LLM 비용·환각 관리 필요
3. **후원 결제(M~L)** — **PG 계약·키가 선행**이므로 계약 절차와 병행. 멱등성 설계는 완료(`donation-payment-idempotency.md`)

---

## 1. 이메일 인증 (Email Verification) — 규모 S

**목적**: 가입 시 이메일 소유 확인 → 가짜 이메일 가입 방지, 알림·재설정 신뢰성 확보.
**선행조건**: 없음(SMTP 설정 완료). 비밀번호 재설정의 토큰 패턴을 그대로 재사용.

### 설계 (비번 재설정과 동일 보안 패턴)
- 스키마: `User.emailVerified DateTime?` + `EmailVerificationToken`(tokenHash unique·expiresAt·usedAt) — `PasswordResetToken`과 동일 구조 재사용
- 토큰: 랜덤 32B, DB엔 sha256만, 만료(예: 24시간), **1회용 조건부 원자 클레임**(재설정과 동일)

### 단계
1. 스키마 + 마이그레이션(`add_email_verification`)
2. 가입 시(`/api/signup`) → 인증 메일 발송(토큰 링크 `/verify-email?token=`)
3. `/verify-email` 페이지 + `/api/verify-email`(토큰 검증 → `emailVerified` 설정, 조건부 원자 클레임)
4. **미인증 정책 결정** (권장: soft):
   - **soft(권장)**: 로그인은 되지만 "이메일 미인증" 배너 + 재발송 버튼. 진입장벽 낮게(비영리 특성)
   - hard: 인증 전 로그인 차단(문턱 높음)
5. 인증 메일 재발송 API(레이트리밋)

### 위험/주의
- 메일 미도착(스팸함) → 재발송 버튼 필수
- 기존 회원 처리: 이미 가입된 회원은 `emailVerified=null` → 소급 강제하지 않고 배너만(또는 무시)

### 재사용 이점
비번 재설정의 토큰 생성·해시저장·조건부 클레임 로직을 거의 그대로 복사 → **공수 최소**.

## 2. AI 챗봇 — 규모 M

**핵심 선결정: 무엇을 하는 봇인가?** (범위를 좁혀야 비용·환각 관리 가능)

| 범위 | 설명 | 평가 |
|---|---|---|
| A. FAQ/안내봇(RAG) | 우리 콘텐츠(FAQ·소식·사업안내·오시는길) 기반 답변 + 신청 유도 | **권장** — 근거 기반, 환각 최소 |
| B. 일반 상담(LLM 직접) | 범용 대화 | 범위·비용·부정확 위험 큼 |
| C. 신청 유도봇 | 대화형으로 참여 신청 접수 | A에 통합 가능 |

**권장: A(RAG) + 간단한 신청 유도.** "정확한 상담은 전화 문의"로 안전망.

### 기술 선택
- **LLM**: Claude(Anthropic API) — 한국어 우수. `NEXT_PUBLIC` 아닌 서버 환경변수로 API 키.
- **RAG**: 사이트 콘텐츠를 임베딩 → 질문 시 유사 문서 검색 → 컨텍스트 주입. 규모가 작으니 **DB에 임베딩 저장 + 코사인 유사도**(또는 소규모 벡터 인덱스)로 충분.
- **UI**: 우하단 플로팅 챗 위젯(client), 스트리밍 응답.

### 단계
1. 범위·톤·"범위 밖" 응답 정책 정의(기획)
2. 콘텐츠 인덱싱: FAQ·소식·사업안내·오시는길 → 임베딩 → DB(`ChatDoc`: content·embedding). 콘텐츠 변경 시 재인덱싱 훅
3. 챗 API(`POST /api/chat`): 질문 임베딩 → 유사문서 top-k → 시스템프롬프트+컨텍스트로 LLM 호출 → 스트리밍
4. 플로팅 챗 위젯 UI(대화 상태, 스트리밍 표시)
5. **남용·비용 제어**: 익명 사용자라 **IP 레이트리밋 필수**, 최대 토큰·일일 호출 상한, **프롬프트 인젝션 방어**(시스템 프롬프트 고정, 사용자 입력 격리)
6. 질문 로깅 → FAQ 보강에 활용(개인정보 주의)

### 위험/주의
- **LLM API 비용** — 사용량 상한·레이트리밋 필수(익명 공개 위젯이라 남용 위험)
- **환각** — RAG로 완화 + "정확한 사항은 전화 문의" 고정 안내, 근거 없으면 모른다고 답하도록 프롬프트
- **프롬프트 인젝션** — 사용자 입력을 지시로 오인하지 않게 격리
- **개인정보** — 대화창에 개인정보 입력하지 않도록 안내, 로그 최소화
- **Hostinger 런타임** — 외부 LLM 스트리밍 호출의 서버 부담·타임아웃 고려(현 커스텀 서버에서 SSE/스트리밍 동작 확인 필요)

## 3. 후원 결제 — 규모 M~L (PG 계약 선행)

**선행조건(필수)**: PG 계약 + 키. 설계는 `donation-payment-idempotency.md`에 완료.

### PG 선택
| PG | 특징 |
|---|---|
| **토스페이먼츠**(직접) | 연동 단순·문서 좋음. 단일 PG |
| **PortOne(구 아임포트)** | 여러 PG 통합·간편결제 다양. 유연 |

비영리·단순 후원이면 **토스페이먼츠** 권장(단순). 결제수단 다양성이 중요하면 PortOne.

### 단계 (설계문서의 승인 기반 플로우 구현)
1. 스키마 확장: `Donation`(orderId·paymentKey **unique**, status, pgProvider, paidAt) + `WebhookEvent`(provider+eventId unique) + 마이그레이션
2. 후원 폼 페이지(`/donate`): 금액 선택(정액 버튼+직접입력, **서버 화이트리스트 검증**), 후원자 정보
3. 주문 생성 `POST /api/donations` → PENDING + orderId 발급
4. PG 결제창 연동(client SDK) → 성공 콜백
5. 승인 `POST /api/donations/confirm` → **PG 서버 직접 승인(외부호출, 트랜잭션 밖)** + 금액 서버 대조 + **조건부 상태전이**(`updateMany where status=PENDING`)
6. 웹훅 `POST /api/webhooks/pay` → **서명 검증** + `eventId` 유니크 멱등 + 동일 전이
7. reconciliation cron(장기 PENDING을 PG 조회로 동기화)
8. 관리자 후원 내역 페이지(`/dashboard/donations`)
9. (선택) 기부금 영수증 — **지정기부금단체 여부 등 법적 요건 확인 필요**

### 검증
PG **테스트 모드(테스트 키)**로: 정상 결제, 웹훅 중복 수신, 부분 실패, 이중 클릭 → 이중 반영 없음 확인.

### 위험/주의
- **이중 결제 방지** — 설계문서대로 orderId·paymentKey·eventId 유니크 + 조건부 전이
- **금액 위변조** — 클라이언트 금액 불신, 서버가 PG로 재확인
- **웹훅 위조** — 서명 검증 필수
- **환불 정책·CS** — 결제 실패/취소/환불 흐름, 개인정보(후원자 정보) 보관 정책
- **법적**: 기부금 영수증·개인정보 처리방침 갱신 검토
